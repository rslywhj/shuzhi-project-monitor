# 微信小程序接入评估

## 1. 结论

当前项目**可以接入微信小程序**，并且现有 Cloudflare Worker、D1、KV、邮件及通知能力可以继续作为统一后端使用。但现有 React Web 页面依赖 DOM、CSS Grid、浏览器全屏和横向滚动，不能原样编译成原生小程序界面。

推荐采用“两阶段”路线：

1. **第一阶段：小程序 WebView 快速接入**
   - 在小程序中通过 `web-view` 打开现有移动端 Web 应用；
   - 复用现有账号、权限、接口和页面；
   - 适合内部试点和快速验证；
   - 需要在微信公众平台配置业务域名，并完成域名校验、HTTPS及相应备案要求。
2. **第二阶段：Taro原生小程序**
   - 使用 React + TypeScript + Taro重写高频移动场景；
   - 继续调用现有 Cloudflare Worker API；
   - Web大屏和桌面工作台继续保留，小程序侧重点改为异常提醒、待办、周报和审批。

## 2. 可复用与需改造范围

### 可直接复用

- Cloudflare Worker API及现有业务接口；
- D1中的项目、节点、周报、风险、措施、基线和快照数据；
- KV附件存储；
- 红黄绿判定、综合健康度、预测预警及权限规则；
- 通知事件和电子邮件、企业微信、钉钉渠道；
- TypeScript类型、字段字典和部分数据转换逻辑。

### 需要改造

- 登录：增加微信 `wx.login` 临时码换取会话，并将 `openid/unionid` 与现有用户账号绑定；
- UI：矩阵不宜在手机上完整平铺12个节点，应改为项目卡片、异常节点列表和单项目时间轴；
- 网络：将 `https://itpm.dougge.top` 配置为小程序合法请求域名和业务域名；
- 附件：使用 `wx.uploadFile`、`wx.downloadFile` 对接现有附件接口；
- 消息：如需微信订阅消息，需新增模板、用户授权和服务端发送能力；
- 会话：小程序建议使用短期访问令牌或自定义请求头，不完全依赖浏览器Cookie。

## 3. 推荐的小程序信息架构

1. **首页**
   - 红黄绿项目数；
   - 我的待办；
   - 本周未报项目；
   - 近期关键节点；
   - 高风险与逾期措施。
2. **项目**
   - 项目卡片列表；
   - 按组织、负责人、健康度筛选；
   - 单项目节点时间轴；
   - 偏差原因与纠偏措施。
3. **填报**
   - 本周进展；
   - 节点完成度；
   - 预测/实际完成日期；
   - 风险措施及附件。
4. **审批**
   - 基线变更；
   - 快照异常；
   - 待办处理。
5. **我的**
   - 微信账号绑定；
   - 角色和项目归属；
   - 通知订阅；
   - 退出绑定。

## 4. 技术建议

- 前端：Taro + React + TypeScript；
- 后端：继续使用当前 Cloudflare Worker；
- 数据：继续使用D1，避免形成小程序独立数据孤岛；
- 身份：`wx.login → Worker /api/auth/wechat → code2Session → 用户绑定 → 平台会话`；
- 安全：服务端校验微信会话，不把 `appSecret` 放入小程序；保留角色、项目归属和操作审计；
- 监控：区分Web、小程序和自动任务的审计来源；
- 发布：开发版、体验版、正式版分别绑定独立环境配置。

## 5. 实施优先级

| 阶段 | 范围 | 目标 |
|---|---|---|
| P0 | 移动端Web优化 | 手机浏览器和WebView可用 |
| P1 | WebView小程序壳、业务域名、账号登录 | 快速内部试点 |
| P2 | 微信账号绑定、订阅消息 | 降低登录和催报成本 |
| P3 | Taro原生首页、项目、填报、审批 | 形成稳定移动工作入口 |

不建议首期在小程序中复刻1920×1080管理大屏。管理大屏继续服务会议和集中态势展示，小程序应聚焦“看异常、收提醒、做填报、批变更”。
